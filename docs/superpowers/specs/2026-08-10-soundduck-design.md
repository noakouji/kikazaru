# Kikazaru 設計

2026-08-10

## 何を作るか

マイクを使っている間だけスピーカーの音量を自動で下げる、macOS のメニューバーアプリ。

現在 Python スクリプトとして動いているものを、常駐に耐える形に作り直す。
アクションを差し替え可能にして Sonos 以外にも広げられるようにし、他人に配布できる形にする。

## 背景

スピーカーから流れる音楽がマイクに回り込み、音声認識の精度を落とす。
本来は AEC（音響エコーキャンセル）で消す問題だが、AirPlay 経由の Sonos は遅延が 2 秒前後あり
別クロックで動くため、AEC の前提が成立しない。

そこで「消す」のをやめ、「喋っている間だけ鳴らさない」方式を採る。
Python 版で実機検証済みで、この方針が有効であることは確認できている。

## 要件

| # | 要件 | 理由 |
|---|---|---|
| R1 | メニューバー常駐（Dock に出さない） | 常に動かすものなので視界を専有しない |
| R2 | 待機中の CPU 使用率が実質ゼロ | 一日中動かすため |
| R3 | アクションを差し替えられる | Sonos 以外（Mac 本体音量など）にも広げたい |
| R4 | 他人に配布できる | 社内・外部に渡せる形にする |
| R5 | 権限なしで基本機能が動く | 配布時の導入障壁を下げる |
| R6 | 音量が下がったまま取り残されない | 事故として最も影響が大きい |
| R7 | オンライン会議でも動く | 実利用時間はディクテーションより長い |

## トリガー設計

マイクとホットキーを併用する。**ホットキーは主役ではなく加速装置**として使う。

```
マイクON        → 下げる      会議・ディクテーション・録音を全部カバー
ホットキー解放   → 即座に戻す   温存時間を待たずに短絡させる
マイクOFF       → 戻す        保険。ホットキーが効かない場合もここで必ず戻る
```

この構成にする理由は、単独案がそれぞれ穴を持つため。

- **ホットキー単独**は、Zoom / Meet / Teams がホットキーを押さないため会議で機能しない（R7 違反）
- **マイク単独**は、Aqua Voice が発話後もマイクを 2〜3 秒温存するため戻りが遅れる

併用すると、ホットキーのイベントを取り逃しても**マイクOFF が最終保険として働くため、音量が下がりっぱなしにならない**（R6）。
Aqua Voice 側でキー設定を変更された場合も、遅くなるだけで壊れない。

トグル式・押しっぱなし式のどちらでも動く。押しっぱなしなら解放イベント、
トグルなら 2 回目の押下を「終了」として扱い、どちらの場合もマイクOFF が保険になる。

## 権限方針

| 権限 | 要否 | 備考 |
|---|---|---|
| マイク | **不要** | デバイスの使用状態のみ読む。音声そのものは扱わない |
| アクセシビリティ | **任意** | ホットキー機構を有効化したときだけ要求。初期値 OFF |
| ネットワーク | 不要 | ローカル LAN への発信のみ |

初期状態では権限を一切要求せずに動く（R5）。
「高速レスポンスを有効にする」を ON にしたときに限りアクセシビリティを要求する。

### DuckAction プロトコル

アクション側が実装するのは 2 つだけ。これが R3 の実体になる。

```swift
protocol DuckAction {
    var name: String { get }
    var isEnabled: Bool { get set }
    func duck(ratio: Double) async
    func restore() async
    func snapshot() -> [String: Int]   // クラッシュ復元用
    func apply(snapshot: [String: Int]) async
}
```

Sonos のコードを一切触らずに、Mac 本体音量・Hue・Slack ステータスなどを追加できる。

### 状態機械

```
idle ──マイクON──▶ ducked ──ホットキー解放──────────▶ restoring ──▶ idle
                     └────マイクOFF + 猶予0.4秒────▶
```

猶予を挟む理由は実測にもとづく。Aqua Voice は発話の切れ目でマイクを閉じて
同一サンプル内で再オープンすることがあり、猶予なしでは音量が上下にばたつく。

## CPU 負荷（R2）

Python 版は 50ms 間隔のポーリングだった。Swift 版では CoreAudio の
`AudioObjectAddPropertyListenerBlock` を使い、状態変化時に OS から通知を受ける。

待機中に実行されるコードがゼロになり、ネットワークに出るのも音量が変わる瞬間だけになる。

Sonos の構成変更（グループの組み替え）への追従は 5 分間隔のタイマーで行う。
Python 版は 60 秒間隔だったが、常駐前提では 5 分で十分であり負荷も下がる。

## 安全機構（R6）

三重に対策する。Python 版で強制終了（`kill -9`）からの復元まで検証済みの方式を踏襲する。

1. 音量を下げる時点で、元の値を Application Support 配下に永続化する
2. 終了シグナルと `applicationWillTerminate` で復元する
3. 起動時に永続化ファイルが残っていれば、前回の異常終了とみなして復元する

## 実装方式

Swift Package Manager の実行可能ターゲットとして作り、ビルドスクリプトで `.app` バンドルに包む。

Xcode プロジェクトを使わない理由は、ターミナルから完結してビルド・検証できるようにするため。
`.app` バンドルと `Info.plist`（`LSUIElement = true`）さえ用意すれば、
メニューバーアプリとしても SwiftUI の設定画面としても正しく動作する。

外部依存はゼロ。CoreAudio・AppKit・SwiftUI・URLSession のみで構成する。

## Sonos 制御で踏んではいけない罠

Python 版の実機検証で判明したもの。実装時に再発見しないよう明記する。

- **`RampToVolume` はダッキングに使えない。** フェードイン専用で、目標値を指定すると
  いったん 0 まで落ちてから目標値へ上がる
- **`RestoreVolumePriorToRamp` は HTTP 500 を返す**（Arc Ultra / ファーム 96.0-79160）
- **親機の `TransportState` は信用できない。** メンバーが再生中でも親機が `STOPPED` を返す。
  再生状態による分岐はしない
- **`GetZoneGroupState` の戻り値は二重 XML エスケープされている**
- グループ再生中は各機が自分の音量を持つため、**可視メンバー全員を個別に制御する**。
  サテライト（Sub・サラウンド）は親機に追従するので除外する
- 音量の反映は速い（`SetVolume` 往復が実測 13ms）。5 段階のフェードで 76ms

## 実装順序

1. Sonos 制御層（Python 版の移植＋動作確認）
2. MicMonitor（イベント駆動）＋ Coordinator ＋ 安全機構
3. `.app` バンドル化とメニューバー UI
4. HotkeyMonitor（任意機能）
5. 設定画面

各段階で実機検証し、動作を確認してから次に進む。

## 対象外

- Sonos 以外のアクションの実装（プロトコルだけ用意し、実装は Sonos と Mac 本体音量のみ）
- 音声レベル判定（VAD）
- 自動アップデート機構
- App Store 配布
